## 2. 成本估算（1000 次请求）

**公式**（记在脑子里，面试会问）：

```
单次成本 = (prompt_tokens × 输入价 + completion_tokens × 输出价) / 1_000_000
1000 次成本 = 单次成本 × 1000
```

**实测 token 数**（用自己的数据，不要用官网示例）：

| 供应商   | 模型          | 平均 prompt tokens | 平均 completion tokens | 单次成本(¥) | 1000 次成本(¥) |
| -------- | ------------- | ------------------ | ---------------------- | ----------- | -------------- |
| 百炼     | qwen3.8-flash | 98                 | 378                    | 0.00110             | 1.10            |
| DeepSeek | deepseek-chat | 42                 | 105                    | 0.00054 / 0.00107   | 0.54 / 1.07     |

> DeepSeek 是**空闲 / 高峰**两档（见上方价格来源）。百炼不分时段。
>
> 注意：这两行总成本**仍然不能直接比"谁便宜"**——DeepSeek 只写了 105 token，百炼写了 378。原因见 2.1。

> 早期样本（`hello_llm.py` + 百炼 qwen-turbo）：prompt=72 / completion=173。与上表不是同一模型、同一 prompt，**不要混用**。

> 换算成"人话"更有说服力：1000 次 ≈ 几次面试？≈ 一杯咖啡的几分之几？

### 2.1 这版数据为什么还不能横比（第一版，2026-11-25）

**结论：这两行数字不能直接比"谁便宜"，因为它比的是"谁话少"。**

| 事实                       | 数字                                               | 含义                                                                        |
| -------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------- |
| 同一句 prompt 的输入 token | 98 vs 42                                           | tokenizer 不同。DeepSeek 切中文更省（约 1.6 字/token），百炼约 0.7 字/token |
| 输出 token                 | 378 vs 105                                         | 回答长度差 3.6 倍——自由发挥的结果，不是能力差异                             |
| 生成速度                   | 378÷4.59 = **82 tok/s** vs 105÷1.41 = **74 tok/s** | 延迟差 3.2 倍是假象，真实速度只差约 10%                                     |

**真正可横比的单价**（与输出长度无关）：

| 供应商                                   | 每百万输出 token | 每千输出 token |
| ---------------------------------------- | ---------------- | -------------- |
| 百炼 qwen3.8-flash                       | ¥2.7             | ¥0.0027        |
| DeepSeek deepseek-chat（空闲时段）       | ¥4.5             | ¥0.0045        |
| DeepSeek deepseek-chat（高峰时段）       | ¥9.0             | ¥0.0090        |

**单价上百炼便宜 1.7–3.3 倍**（取决于调用时段）。表 2 里 DeepSeek 的总成本更低，**纯粹因为它只写了 105 token**，不是因为它便宜。

**补充证据（2026-11-26 压测，`max_tokens=5` 极短输出）**：
百炼中位 **0.81s**，DeepSeek 中位 **0.86s**——几乎一样。
说明两家的**基础开销（网络往返 + 首字生成）基本相同**，表 1 里 3 倍的总耗时差距**完全来自输出长度**。
反过来说：如果你的任务输出很短（分类、抽取、判断），选哪家延迟都差不多；输出越长，差距才越明显。

> **教训（面试会问）**：
> ① 比价格用单价，不用总价；
> ② 比速度用 tok/s，不用总延迟；
> ③ 想横比总成本，必须先让输出长度可比（强约束格式 + `max_tokens` 兜底）。
>
> **已核对（2026-11-26）**：表 1 模型名已统一为 `deepseek-chat`；原抄录的 `2 / 8` 是 2026-08-17 调价前的旧价，已按官方峰谷价更正。

### 2.2 成本直觉（手算练习，2026-11-25）

样本：DeepSeek 一次调用，42 输入 / 105 输出 token，单价 2 元 / 8 元每百万 token。

> 下面这组算式用的是**当时抄录的 2 / 8**（现已更正为峰谷价 1.5–3 / 4.5–9）。数字会变，**方法不变**——这节练的是「单次 → 次数 → 天数」三层估算的顺序，不是背某个价。

| 问题                    | 算式                                            | 结果                       |
| ----------------------- | ----------------------------------------------- | -------------------------- |
| 单次成本                | (42×2 + 105×8) ÷ 1,000,000 = 924 ÷ 100万        | **¥0.00092**（约 0.09 分） |
| 每天 500 次，一月 30 天 | 0.00092 × 500 × 30 = 15,000 次                  | **¥13.86 / 月**            |
| 输出涨到 400 token      | (42×2 + 400×8) ÷ 100万 = 3284 ÷ 100万 = 0.00328 | **¥0.00328，3.55 倍**      |

**三个要点**：

1. **输出涨 3.8 倍（105→400），成本只涨 3.55 倍**——因为输入那 42 token 没变，被摊薄了。所以"回答变长"对成本的冲击，小于长度本身的倍率。
2. **一个月 15,000 次 ≈ ¥13.86，每天不到 5 毛**——这个阶段成本完全不是瓶颈，调试、评测、反复重跑都可以放开做。真正贵的是你的时间。
3. **除数是 1,000,000**，因为单价是"每百万 token"。写成 1000 会错三个数量级，这是最常见的错。

> 反向用法：面试被问"这个功能一个月多少钱"，先问清 QPS 或日调用量，再按这个三层算式估——**先算单次，再乘次数，最后乘天数**。

| 中文语感（/50） | 44.0               | 44.0                   | 持平      |

**两题值得单独记：**

- **Q2 幻觉**：百炼在"不存在的文件"上编出了条文（2.5 分），DeepSeek 明确说无法确认（4.5 分）。**这一题的信息量超过其余九题**——它直接决定 RAG 项目的 faithfulness，也决定 agent 会不会瞎编工具返回。
- **Q3 算术**：两家第二问**都算错**（各 2.5 分）。不是谁强谁弱，是模型通病。启示：涉及数字就让模型输出算式、由代码验算，别直接信结论。

> **盲评规则**：两份答案打乱成 A/B，先打分后揭晓。提前知道谁的答案，评出来的就不是模型能力，是你的印象。

## 4. 限流实测

| 供应商   | 实验        | 触发情况 | 实际 QPS | 结论                     |
| -------- | ----------- | -------- | -------- | ------------------------ |
| 阿里云百炼 | 0.5s × 8 次 | 未触发   | ≈ 0.73   | 安全区内                 |
| 阿里云百炼 | 0.2s × 8 次 | 未触发   | ≈ 0.81   | 压 sleep 几乎没用，见下  |
| DeepSeek | 0.5s × 8 次 | 未触发   | ≈ 0.68   | 安全区内                 |
| DeepSeek | 0.2s × 8 次 | 未触发   | ≈ 0.94   | 同左                     |

> **测法**：`rate_test.py`，`max_retries=0`（关键——不关掉 SDK 自动重试就永远看不到真正的 429），`max_tokens=5` 压成本。

**这次实验的方法缺陷（比结果重要）**：

把 `INTERVAL` 从 0.5 改成 0.2，实际 QPS 只从 0.73 涨到 0.81——**几乎没变**。

原因是**串行调用**：每次要等上一次返回（0.5–1.2s）才发下一次。发送间隔由「响应时间 + sleep」决定，不是由 sleep 决定：

```
实际间隔 ≈ 响应时间(约 0.9s) + sleep(0.2s) ≈ 1.1s  →  约 0.9 QPS
```

**所以串行循环永远压不出限流。** 要测真实阈值必须并发（`asyncio.gather` 或线程池同时发 10–20 个），那是 W17（异步/队列）的内容。

**当前可下的结论**：
- ✅ 低频使用（≤1 QPS）不会撞限流，Agent 单步调用、评测批量跑都在安全区
- ❌ 不能说"这两家限流宽松"——**阈值未知**，且百炼是动态限流（TPM 按账号月消费分档），换档位就变
- ⏸ 阈值测量**主动放弃**：测到了也没有决策价值（额度档位会变），且猛试有封号风险。留到 W17 用并发做。

> 测法：每隔 1 秒发一次，记录第几次开始报 429。**不要写 while 死循环猛试**，会被封更久。

## 5. 日志脱敏（W1 完成标准之一）

实现：`code/w01-llm-basics/safe_log.py`（`ruff` 通过，已实跑验证）

- [x] 日志里不打印完整 key：`mask()` 只留前 4 位，实测输出 `sk-w****…****`
- [x] 异常堆栈不带出 key：手动触发 404（`model="not-exist-model-xyz"`），完整 traceback 里搜不到 `sk-`
- [x] 演示已做，输出见当日记录

**两层防线**（这是关键设计）：

1. **入口打码**：调用 `mask(key)` 再进日志
2. **出口过滤**：`SecretFilter` 挂在 handler 上，用正则把任何形如 `sk-xxxx` 的串替换掉

第二层的意义：**即使以后有人写了 `log.info(f"key={key}")` 这种代码，也漏不出去**。`print` 做不到这一点——它散落在各处，没法统一拦截。

**三个必须防住的边界**：

| 边界 | 后果 | 处理 |
| --- | --- | --- |
| 赋值时多一个逗号 → `("sk-xxx",)` | `len()` 变成 1，走进"短串"分支**原样输出**，且不报错 | `str()` 强制转换 + 短串全遮 |
| key 为 `None` | `len(None)` 抛 TypeError，报错信息误导人 | 先判空，返回 `<empty>` |
| 短字符串（≤8 位） | 遮不全等于没遮 | 一律全遮 |

> **实战教训**：`api_key=os.getenv("..."),` 末尾多一个逗号，Python 会把它当**元组**。程序不报错、日志正常写、监控全绿，但完整 key 已经进了日志。
> **崩溃的 bug 是好 bug，静默的 bug 是灾难。** 看到输出带 `('...',)` 就先查 `type()`。

## 6. 结论（写完这节才算 W1 结束）

1. **最便宜的是**：**百炼**。按单价，输出 ¥2.7 / 百万 token；DeepSeek 是 ¥4.5（空闲）～¥9（高峰），**贵 1.7–3.3 倍**。不能用"1000 次总成本"比，那是被输出长度污染的假象（见 2.1）。
2. **最快的是**：**百炼**，按生成速度 82 vs 74 tok/s，快约 10%。但**端到端总耗时 DeepSeek 更快**（1.41s vs 4.59s），因为它写得短。两个指标回答的是两个问题：用户体感看总耗时，模型能力看 tok/s。
3. **中文最好的是**：**没有明显差别**。准确性 41.5 vs 40.5（差 2%，在人工评分噪声内），语感 44 vs 44。但**分工不同**：该说"不知道"时 DeepSeek 更可靠（Q2：4.5 vs 2.5，百炼对着不存在的文件编了条文）；该守格式时百炼更稳（Q1：DeepSeek 超字数被扣到 2 分）。
4. **练手推荐用**：**DeepSeek**。理由不是"更好"，是"错得更便宜"——输出短所以总成本低、响应快所以反馈快、乱编倾向更低。练手阶段试错次数多，这三点比单价重要。
5. **正式项目推荐用**：**按场景选，不选单一赢家**——
   - 长输出（摘要、报告、长回答）→ **百炼**：输出单价低 1.7–3.3 倍，tok/s 也更快
   - 短输出（分类、抽取、判断）→ **两家都行**：延迟几乎相同（0.81s vs 0.86s），按价格和稳定性选
   - 需要"该说不知道就说不知道"（RAG 问答、客服）→ **DeepSeek**：Q2 幻觉测试 4.5 vs 2.5
   - 限流：2 QPS 两家都稳，但**都没测到阈值**，上量前必须补测
