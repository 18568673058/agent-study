## 学到的概念

1. **盲评（blind evaluation）**
   - 是什么：打分时不知道哪个答案是谁写的
   - 为什么需要：知道来源就会带偏见，"我印象里 DeepSeek 中文好"会直接影响分数
   - 什么时候用：所有主观质量评估。LLM-as-judge 也要抽样人工盲评校准

2. **限流有两个维度：RPM（频率）和 TPM（总量）**
   - 频率问题用限流器（令牌桶/漏桶）解决
   - 总量问题只能靠预算和降级
   - 判断方法：改请求间隔看触发点是否提前——提前就是频率问题

3. **`logging` 的 Filter 机制 vs `print`**
   - `print` 散落在代码里，无法统一拦截
   - `logging` 可以在 handler 上挂 Filter，一处配置全局生效
   - 代码里靠人记得打码，但人一定会忘；结构性的防线才可靠

4. **峰谷定价会改变成本结论**
   - DeepSeek 2026-08-17 起：高峰（9-12、14-18 点）价格是空闲时段的 2 倍
   - 同一个任务，工作日下午跑和周末跑，成本差一倍
   - 推论："错峰调用"是真实可用的成本优化手段

5. ~~固定模板开销主导短请求成本~~ **—— 2026-11-27 撤回**

   - **当时的判断**：7 个汉字的 prompt 消耗 65 个 prompt token，所以大头是 chat 模板
   - **为什么撤回**：11-27 用同一句「回复一个字：好」测 DeepSeek，只有 **18 token**，差 3.6 倍
   - **这说明什么**：不是"所有模型都有 60 token 固定开销"，而是**百炼的模板开销远大于 DeepSeek**，属于厂商差异
   - **能可靠说的**：跨平台比成本必须用同一请求分别实测，不能按字数折算
   - **方法论教训**：**单点数据只能提出假设，不能下结论。** 当时一个数据点就写成了普遍规律，第二天就被推翻

## 踩的坑

### 坑 1：赋值末尾多一个逗号，密钥静默泄露
- **现象**：程序不报错，日志输出 `('sk-xxx',)`
- **原因**：`api_key=os.getenv("..."),` 末尾的逗号让 Python 把它当**元组**。`len()` 变成 1，走进"短字符串"分支，原样返回
- **解法**：删掉逗号；`mask()` 里加 `str()` 兜底
- **下次怎么避免**：**看到输出带 `('...',)` 就查 `type()`**。这是最危险的一类 bug——不崩、不报警，静默泄露。崩溃的 bug 是好 bug

### 坑 2：串行循环压不出限流
- **现象**：`INTERVAL` 从 0.5 降到 0.2，QPS 只从 0.73 涨到 0.81，没触发 429
- **原因**：串行调用必须等上一次返回（0.5–1.2s）才发下一次。实际间隔 = 响应时间 + sleep，瓶颈是响应时间不是 sleep
- **解法**：**放弃测阈值**。要压出 429 必须并发（`asyncio.gather`），那是 W17 的内容
- **判断**：不是所有能测的都值得测。阈值是动态的（按账号消费分档），测到也没决策价值

### 坑 3：抄的价格是旧价
- **现象**：DeepSeek 单价抄成 2 / 8
- **原因**：那是 2026-08-17 调价前的价格。现价是峰谷两档（输入 1.5–3，输出 4.5–9）
- **下次怎么避免**：抄价格必须看页面上的生效日期；跨月的价格资料要重新核对

### 坑 4：结论里把"单价"和"总成本"混用
- **现象**：写"最便宜的是百炼，1000 次约 ¥0.0027"——0.0027 其实是每千 token 的单价
- **原因**：两个概念用的是同一个"便宜"字
- **解法**：比价格用**单价**（每千输出 token），比总成本必须先让输出长度可比
